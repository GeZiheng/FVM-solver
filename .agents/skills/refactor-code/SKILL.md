# Refactor-Code 工作流

对现有代码的重构/修改必须严格按照以下四个阶段顺序执行，不得跳过或合并阶段。每个阶段的准入/准出条件必须满足后才能进入下一阶段。

## 通用规则

- **最小改动**：只改实现重构目标所必需的代码，不顺手做无关修改。
- **不改动既有测试逻辑**：重构改变接口时只修复调用点，不修改测试的既有断言语义。
- **编译与测试**：优先使用项目提供的 `build-and-test` MCP 工具（参数 config/target/run，默认 Release、all、tests）。涉及 `python/`、pybind11 绑定或 `pyfvm_tests` 的改动，验证必须额外以 `python=true` 跑一轮（ctest 含 `pyfvm_tests`，见阶段 2）。该工具不可用时，先读项目 `AGENTS.md` 的构建说明——其手动命令位于 `README.md`——再按其中方式构建，不要凭猜测直接敲构建命令。
- **用户确认**：所有需要用户确认的节点，直接在回复里向用户提问并等待答复，不要替用户默认同意。
- **进度跟踪**：方案拆分为多步时，维护一份步骤清单并实时更新状态（有计划工具就用工具，没有就用文字列在回复里）。
- **按门槛委派执行**：环境提供项目子 agent 时，把边界内**过委派门槛**的执行类任务交给对应 flash 子 agent（阶段 2 代码编辑 → `fvm-implementer`、阶段 4 文档更新 → `fvm-docs`），未过门槛的由父 agent 直接执行；阶段 3 有界 diff 审查 → `fvm-reviewer` 为整 diff 一次、不设门槛。委派策略（规模/设计/价值三道门、越界与记账、父 agent 保留职责）以项目 `AGENTS.md` 的「Codex Subagent Policy」为唯一出处，本技能只做阶段映射、不复述门槛数值。
- **Git 写操作需用户明确授权**：`git add` / `commit` / `reset` / `push` 等改变仓库状态的操作，必须等用户**明确说出**要做（如"提交"）之后才执行；`status` / `diff` / `log` 等只读命令不受限。用户说"先不用提交""改完一起提交"只是在说明提交方式，**不构成提交授权**；任务结束时只报告"可以提交"，不代用户决定提交时机、拆分方式与提交信息。

## 阶段 1：制定重构方案

1. 阅读相关代码，理解现状与用户的重构目标。
2. 输出一份详细方案，内容包括：
   - 重构目标与范围（明确哪些文件/模块会受影响）；
   - 接口/结构的变化点；
   - 所有受影响的调用点清单；
   - 对测试的影响分析。
3. 若任务步骤多，**拆分成可独立编译的步骤组**，并按 `AGENTS.md` 委派门槛为每组标注执行者（父 agent / `fvm-implementer`，随方案一并确认）；触及求解器敏感路径或测试基础设施的组还需能独立通过全量测试（验证粒度按阶段 2 的分组规则执行）。
4. **复杂方案落盘**：方案拆成 >= 2 个步骤组、或包含求解器敏感/数值设计时，把完整方案写入 `.agents/plans/<主题>.md`（该目录已被 gitignore，是阶段性工作工件，不替代阶段 4 的文档更新）。文档结构：目标与范围、设计决策（公式、符号/索引约定、边界处理）、步骤组与调用点、验证策略、风险、变更记录，顶部状态字段记录确认日期。回复里只给**摘要**：目标、步骤组与执行者、关键设计决策、风险、验证策略、文档路径——摘要必须让用户不看全文也能确认全部载荷决策。简单方案（单步骤组且无数值设计）不落盘，直接写在回复里。
5. 根据用户反馈调整方案，直到用户明确确认；已落盘的方案先更新计划文档（含变更记录），再给出修订摘要。

**约束：**
- 本阶段**禁止修改任何代码**；除 `.agents/plans/` 下的计划文档外不得写入任何文件（其余只允许只读操作：读文件、搜索、查看测试结果）。
- **必须获得用户确认**后才能进入阶段 2。

## 阶段 2：修改代码

1. 严格按阶段 1 确认的方案执行，不擅自扩大改动范围。
2. 若方案拆为多步，按**可独立编译的步骤组**组织：每组完成后先做编译检查（build-and-test `run=none`），父 agent 快速审查该组 diff（先 `git diff --stat`，再看涉及的 hunk）后再进入下一组；**全量 ctest 在阶段 2 收尾统一运行**。任一组触及求解器敏感路径（清单见 `AGENTS.md`「Codex Subagent Policy」）或测试基础设施时，该组结束即运行全量测试。未拆步则改完后统一验证。改动涉及 `python/`、pybind11 绑定或 `pyfvm_tests` 时，验证必须包含一轮 `python=true` 的 build-and-test。
3. 编译或测试失败：分析原因并继续修复，直到通过。
4. **按门槛委派**：环境提供 `fvm-implementer` 时，**过委派门槛**的代码编辑组委派执行，并遵循 `AGENTS.md`「Codex Subagent Policy」的**持久会话模式**、简报/报告格式与全部三道门（求解器敏感组的设计完备简报要求同见该政策，此处不复述）；已落盘方案的简报以「计划文档 §x + 组内增量」携带共享设计，未落盘的简单方案由简报自带全部设计。执行中方案发生修订（stop-and-report 答复、用户调整）时，先更新计划文档（含变更记录），并在下一条简报中告知子 agent 重读；未过门槛的组由父 agent 直接执行。
5. **熔断条件**：若同一步反复修改验证多次（约 3~5 轮）仍无法通过，**停下来**，向用户报告：当前步骤、已尝试的方案、失败现象、自己的判断，等待用户指示。

**约束：**
- 本阶段**无需用户参与**，自主迭代直到全部测试通过或触发熔断。
- 正常完成（或熔断停下报告后）自动进入阶段 3。

## 阶段 3：代码审查

1. 先向用户报告阶段 2 的执行情况：每一步完成了什么、编译/测试是否通过、最终改动概览（可用 `git diff` 辅助说明）。
2. 回答用户对实现细节的提问，解释设计取舍。
3. **默认委派**：有界 diff 的结构/风格审查（命名、依赖方向、include/别名、测试覆盖、ASCII 合规、文档影响）默认委派 `fvm-reviewer` 只读执行；数值方法结论等父/子职责边界按 `AGENTS.md`「Codex Subagent Policy」执行。
4. **用户要求继续调整代码时：不得直接修改，必须返回阶段 1**，针对新需求制定（或修订）方案，经确认后再走阶段 2。
5. 用户没有新问题、无需调整时，进入阶段 4。

**约束：**
- 本阶段**禁止修改代码**。

## 阶段 4：更新文档

1. 列出需要更新的文档清单，并说明每个文档的更新内容。文档位置约定（项目 `AGENTS.md` 已有约定时以它为准）：
   - `docs/<模块名>.md`：模块的类结构、设计思路、关键算法/公式——凡改动了某模块的类、接口或算法，必须更新对应文件；
   - `AGENTS.md`：架构图、项目状态、构建/约定等结构性说明有变化时更新；
   - `README.md` 等其他文档：涉及用户可见的用法变化时更新。
2. **按门槛委派**：过委派门槛的文档更新委派 `fvm-docs` 执行（父 agent 提供改动说明与文档清单，保持中文文档约定；已落盘方案可让子 agent 直接引用计划文档作为改动说明）；未过门槛的文档改动由父 agent 直接更新。
3. **经用户确认后**才开始修改文档。
4. 更新后用户如需调整，继续修改直到用户满意。

**约束：**
- 本阶段只修改文档，不修改代码；如发现代码问题，返回阶段 1。

## 收尾：任务总结

四个阶段全部完成后，输出一份总结，包括：
- 重构目标与最终方案的对应关系；
- 各阶段的关键结果（改动文件、测试状态、文档更新清单）；
- 遗留问题或后续建议（如有）。

总结完成后**停在"可以提交"**：给出建议的提交信息或拆分方式，等用户明确指示后再执行 git 写操作（见通用规则）。
