# Refactor-Code 工作流

对现有代码的重构/修改必须严格按照以下四个阶段顺序执行，不得跳过或合并阶段。每个阶段的准入/准出条件必须满足后才能进入下一阶段。

## 通用规则

- **最小改动**：只改实现重构目标所必需的代码，不顺手做无关修改。
- **不改动既有测试逻辑**：重构改变接口时只修复调用点，不修改测试的既有断言语义。
- **编译与测试**：本项目统一使用 `build-and-test` 工具编译和运行测试（默认 Release、target=all、run=tests），不要直接调用 cmake/ctest/ninja。
- **用户确认**：所有需要用户确认的节点，使用 `question` 工具询问，不要在普通回复里默认用户已同意。
- **进度跟踪**：方案拆分为多步时，用 `todowrite` 维护步骤清单并实时更新状态。

## 阶段 1：制定重构方案

1. 阅读相关代码，理解现状与用户的重构目标。
2. 输出一份详细方案，内容包括：
   - 重构目标与范围（明确哪些文件/模块会受影响）；
   - 接口/结构的变化点；
   - 所有受影响的调用点清单；
   - 对测试的影响分析。
3. 若任务步骤多，**拆分成多个小步**，且每一步都能独立编译并通过测试验证。
4. 根据用户反馈调整方案，直到用户明确确认。

**约束：**
- 本阶段**禁止修改任何代码**（允许只读操作：read/glob/grep/查看测试结果）。
- **必须获得用户确认**后才能进入阶段 2。

## 阶段 2：修改代码

1. 严格按阶段 1 确认的方案执行，不擅自扩大改动范围。
2. 若方案拆为多步：每完成一步，立即用 `build-and-test` 编译并运行测试，**该步编译和测试全部通过后才能开始下一步**；未拆步则改完后统一验证。
3. 编译或测试失败：分析原因并继续修复，直到通过。
4. **熔断条件**：若同一步反复修改验证多次（约 3~5 轮）仍无法通过，**停下来**，向用户报告：当前步骤、已尝试的方案、失败现象、自己的判断，等待用户指示。

**约束：**
- 本阶段**无需用户参与**，自主迭代直到全部测试通过或触发熔断。
- 正常完成（或熔断停下报告后）自动进入阶段 3。

## 阶段 3：代码审查

1. 先向用户报告阶段 2 的执行情况：每一步完成了什么、编译/测试是否通过、最终改动概览（可用 `git diff` 辅助说明）。
2. 回答用户对实现细节的提问，解释设计取舍。
3. **用户要求继续调整代码时：不得直接修改，必须返回阶段 1**，针对新需求制定（或修订）方案，经确认后再走阶段 2。
4. 用户没有新问题、无需调整时，进入阶段 4。

**约束：**
- 本阶段**禁止修改代码**。

## 阶段 4：更新文档

1. 列出需要更新的文档清单，并说明每个文档的更新内容。文档位置约定：
   - `docs/<模块名>.md`：模块的类结构、设计思路、关键算法/公式——凡改动了某模块的类、接口或算法，必须更新对应文件；
   - `AGENTS.md`：架构图、项目状态、构建/约定等结构性说明有变化时更新；
   - `README.md` 等其他文档：涉及用户可见的用法变化时更新。
2. **经用户确认后**才开始修改文档。
3. 更新后用户如需调整，继续修改直到用户满意。

**约束：**
- 本阶段只修改文档，不修改代码；如发现代码问题，返回阶段 1。

## 收尾：任务总结

四个阶段全部完成后，输出一份总结，包括：
- 重构目标与最终方案的对应关系；
- 各阶段的关键结果（改动文件、测试状态、文档更新清单）；
- 遗留问题或后续建议（如有）。
